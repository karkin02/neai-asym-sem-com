# Architecture A: Co-Located Edge VLA

Architecture A runs an embodied vision-language-action policy locally:

```text
instruction + two camera views + robot state
                    |
                    v
              local SmolVLA
                    |
                    v
          six SO-101 joint targets
                    |
                    v
          MuJoCo execution + logging
```

The project includes a six-actuator SO-101-compatible MuJoCo environment,
scripted demonstration collection, LeRobot v3 dataset conversion, SmolVLA
fine-tuning, deterministic simulation evaluation, replay export, and
failure/escalation diagnostics.

## Fresh Clone Setup

Generated environments, Hugging Face caches, datasets, model checkpoints, and
evaluation outputs are intentionally excluded from Git. A clone contains the
reproducible source and configuration, but the selected fine-tuned checkpoint
must be restored separately or regenerated by training.

### CPU development

Install 64-bit Python 3.12, then run from the repository root:

```powershell
py -3.12 -m venv .venv312
& ".\.venv312\Scripts\python.exe" -m pip install --upgrade pip
& ".\.venv312\Scripts\python.exe" -m pip install `
  torch==2.11.0 torchvision==0.26.0 torchaudio==2.11.0 `
  --index-url https://download.pytorch.org/whl/cpu
& ".\.venv312\Scripts\python.exe" -m pip install -r requirements.txt
& ".\.venv312\Scripts\python.exe" -m unittest discover -s tests -v
```

This path supports tests and CPU simulation. It is not the recommended training
configuration for this project.

### Windows AMD ROCm

Create and validate the ROCm environment in this order:

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\setup_rocm_windows.ps1
powershell -ExecutionPolicy Bypass -File .\scripts\install_lerobot_rocm.ps1
```

The first script installs the matched gfx1103 PyTorch stack from AMD's wheel
index. The second installs this project and LeRobot, verifies that pip did not
replace ROCm PyTorch, runs a GPU matrix multiplication, and checks package
metadata. Do not install `requirements.txt` first on this path because ordinary
PyPI may select a non-ROCm PyTorch build.

### NVIDIA CUDA

NVIDIA is supported through official PyTorch CUDA wheels. The Windows setup
script defaults to CUDA 12.8 and also accepts the `cu126` and `cu130` PyTorch
2.11 wheel channels:

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\setup_nvidia_windows.ps1
```

Select a different wheel channel when required by the installed NVIDIA driver:

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\setup_nvidia_windows.ps1 `
  -CudaWheel cu126
```

The script creates `.venv312-cuda`, installs the matched PyTorch, torchvision,
and torchaudio wheels, installs LeRobot, verifies a GPU matrix multiplication,
and ensures pip did not replace the CUDA build. Published wheel commands are
listed in PyTorch's official previous-version table:
https://pytorch.org/get-started/previous-versions/

Run inference using the NVIDIA environment:

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\run_architecture_a_smolvla.ps1 `
  -Environment .venv312-cuda `
  -Device cuda `
  -Episodes 1 `
  -GuiReplay
```

Training uses the same selector:

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\train_smolvla.ps1 `
  -Environment .venv312-cuda `
  -Steps 500 `
  -BatchSize 1
```

PyTorch exposes both NVIDIA CUDA and AMD HIP devices through the `torch.cuda`
API, so the Python model and evaluator remain vendor-neutral.

### Restore the selected checkpoint

Place the separately distributed checkpoint directory at:

```text
outputs/train/smolvla_pickplace_50/checkpoints/001500/pretrained_model
```

Then create the `last` directory link expected by
`config/architecture_a_model.json`, or update that manifest to the restored
directory. On Windows PowerShell, a copy works when symbolic-link permission is
not available:

```powershell
$source = ".\outputs\train\smolvla_pickplace_50\checkpoints\001500\pretrained_model"
$target = ".\outputs\train\smolvla_pickplace_50\checkpoints\last\pretrained_model"
New-Item -ItemType Directory -Force (Split-Path $target) | Out-Null
Copy-Item -Recurse -Force $source $target
```

The checkpoint is approximately 0.84 GB and is not suitable for ordinary Git
history. Distribute it through a release asset, Hugging Face Hub, object storage,
or Git LFS. Without it, simulation tests and scripted warehouse demos still run;
only trained SmolVLA inference is unavailable.

## Warehouse exception demo

The warehouse scenario renders a package, conveyor, inspection/rejection zones,
and a missing-barcode exception in MuJoCo. It prints the compact scene graph,
routes the package to inspection, and holds the final pose until the window is
closed:

```powershell
& ".\.venv312-rocm\Scripts\python.exe" .\scripts\run_warehouse_scenario.py `
  --scenario barcode_missing
```

Every warehouse run writes an Architecture B handoff under
`outputs/warehouse_demo/<scenario>-<timestamp>/`:

- `scene_graph.json`: compact observed state with no camera frames
- `decision_trace.json`: mock VLA/LLM proposal and validator decision
- `result.json`: physical outcome, routing, and safety status

The runner exposes simulated VLA uncertainty and Architecture B perception
contracts:

```powershell
& ".\.venv312-rocm\Scripts\python.exe" ".\scripts\run_warehouse_scenario.py" `
  --scenario warehouse_normal `
  --vla-confidence 0.55 `
  --detection-confidence 0.92 `
  --clip-confidence 0.92 `
  --intervention-threshold 0.70
```

Architecture A gates on estimated VLA action confidence, confidence derived from
the real MuJoCo IK residual, joint-limit margin, action-change smoothness, and a
collision-clearance hard gate. Real VLA runs can estimate action confidence from
chunk smoothness and disagreement between consecutive predictions; it is not a
calibrated probability. When the gate fails, the validator executes zero joint
commands and sends the image and robot state to Architecture B. B then runs YOLO,
CLIP, scene-graph construction, and LLM reasoning in that order. In this demo the
VLA, YOLO, and CLIP values are explicit simulated contracts.

Use `--scenario warehouse_normal` to render an intact package with a visible
barcode and route it to the moving conveyor. The package travels to the right
and drops into the green outbound bin. This scenario runner uses
deterministic IK actions to demonstrate the edge/cloud handoff; it does not
change the frozen SmolVLA benchmark.

Use `--scenario package_damaged` to display a red damage mark and route the
package to the yellow rejection zone:

```powershell
& ".\.venv312-rocm\Scripts\python.exe" ".\scripts\run_warehouse_scenario.py" --scenario package_damaged
```

The simulated damage cue is placed on the package front and side, so an overhead
view can miss it. The `condition: damaged` field is injected scenario metadata;
this project does not claim a trained visual damage detector.

Use `--scenario unexpected_obstacle` to place a visible orange safety barrier
in the arm's path. The demo prints a mock VLA proposal to
continue, a mock LLM `stop` review, and a deterministic validator rejection.
The robot remains at home and exports `blocked: true`.

For the unsafe baseline, use `--scenario obstacle_vla_violation`. It bypasses
Architecture B and executes the conveyor proposal despite the blocked path.

Run both obstacle scenes as a sequential comparison with one command. Close the
first MuJoCo window to advance from the unsafe collision to the protected stop:

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\run_obstacle_comparison.ps1
```

Run the semantic policy comparison with the same visibly damaged package. The
first phase wrongly ships it; the second phase applies the LLM review and sends
it to the yellow rejection tray:

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\run_damage_comparison.ps1
```

Results are written under `outputs/architecture_a_demo/<timestamp>/`:

- `episode_XXXX.gif`: overhead replay
- `metrics.json`: success, latency, action bounds, failure reason, and escalation

The accuracy-first runner executes raw model actions. For a steadier
presentation replay, enable zero-phase arm smoothing:

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\run_architecture_a_smolvla.ps1 `
  -Episodes 3 `
  -Seed 1010 `
  -Device cuda `
  -ActionSmoothing 0.35
```

This visual mode scored 10/20 versus 12/20 without smoothing, so it is not the
production default.

## Failure Handling

The evaluator classifies unsuccessful episodes as:

- `invalid_policy_action`
- `grasp_failed`
- `object_not_released`
- `placement_failed`

Failures set `escalation_recommended` in the episode record. The evaluator also
records how many policy commands exceeded the simulated robot's action range.

The Architecture A PowerShell demo defaults to `-Scene warehouse_normal`, which
renders the package, barcode, blue inspection tray, yellow rejection tray,
conveyor, and green outbound bin around the real SmolVLA execution. This complete
warehouse layout is out of distribution for the selected checkpoint, which was
trained on the simpler red-sample two-tray scene; use `-Scene pick_place` when
measuring checkpoint accuracy rather than demonstrating the integrated layout.

Failed or low-consistency SmolVLA episodes export an Architecture A-to-B handoff
as `escalation_XXXX.json` plus one `escalation_XXXX.png` evidence frame. The JSON
contains the instruction, robot state, package/target state, and A's confidence
signals. YOLO, CLIP, scene-graph construction, and LLM reasoning are marked
`pending` because Architecture B owns those stages.

Each real SmolVLA action chunk is validated before entering the execution queue.
Architecture A stops on non-finite actions, joint-bound violations, VLA action
consistency below the configured threshold, or a forward-kinematic MuJoCo contact
between the arm and the physical obstacle. Use `-Scene unexpected_obstacle` to
exercise the pre-execution collision handoff.

Run the complete normal, exception, protected-obstacle, and unsafe-bypass matrix
with `python scripts/validate_warehouse_integration.py`. It writes a versioned
`validation_report.json` and exits nonzero if any expected physical or safety
outcome differs. A-to-B requests are also atomically published under each
evaluation run's `handoff` directory using `architecture_a_to_b/v1`. B replies
with `architecture_b_to_a/v1`; the shared validator accepts only `STOP`, `RETRY`,
`REROUTE`, or `CONTINUE`, checks request IDs and confidence, and enforces local
warehouse rules before any recovery is approved.

Fixed-interval replanning is available with `-ReplanEvery`, but experiments
showed that it disrupted the learned trajectory phase and did not improve
success. Open-loop execution remains selected.

## Fine-Tuning

The training wrapper accepts optimizer steps, physical batch size, source
checkpoint, dataset root, repository ID, and run name:

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\train_smolvla.ps1 `
  -Steps 500 `
  -BatchSize 1 `
  -Checkpoint ".\outputs\train\smolvla_pickplace_50\checkpoints\last\pretrained_model" `
  -DatasetRoot "outputs\lerobot_dataset_90_hard" `
  -DatasetRepoId "local/architecture_a_so101_pickplace_90_hard" `
  -RunName "experiment_name"
```

`Steps` means optimizer updates, not epochs. Batch size 1 is used because
SmolVLA activations, two camera streams, gradients, and optimizer state must fit
in the Radeon 780M's shared memory.

Further fine-tuning is currently not recommended: multiple additional runs
reduced held-out success.

## Scope

The MuJoCo robot uses approximate primitive geometry with SO-101-compatible
joint names and six-dimensional absolute actions. It is an integration test
environment, not a mechanical digital twin. Real-hardware deployment still
requires calibration, hardware-specific action limits, an emergency stop, and
validated observation adapters.

Architecture B should import the same simulator through the neutral boundary:

```python
from shared.environments import SO101MuJoCoEnvironment
```

The compatibility implementation remains in `architecture_a.so101_env` while
Architecture B is developed. This keeps existing datasets, scripts, and saved
commands working without giving B a direct dependency on A's public API.

## Real SO-101 Boundary

The hardware-neutral action adapter is available through:

```python
from shared.robots import (
    JointCalibration,
    SO101ActionAdapter,
    SO101ObservationAdapter,
)
```

It validates six finite commands, applies per-joint offset and scale, rejects
mapped values outside configured limits, and provides a latched emergency stop.
Dry-run mode is enabled by default and does not write to the transport.

The observation adapter reads named overhead and wrist RGB cameras plus all six
joint positions. It validates image shape and pixel type, reverses hardware
calibration into model-space state, and emits the camera/state/task keys used by
the SmolVLA preprocessing pipeline.

`SO101DryRunController` joins observation, policy, and action adapters for one
safe cycle. It measures policy latency and recommends escalation when sensor
validation fails, inference raises an error, inference exceeds its deadline, or
the calibrated action is rejected. A successful dry-run cycle returns the exact
hardware-space command without writing it to a robot transport.

`config/so101_calibration.example.json` is intentionally marked
`EXAMPLE_ONLY_NOT_CALIBRATED`. Do not enable hardware output until a physical
arm has been measured and a reviewed calibration file has replaced the example.
